# Оценка качества поиска

Этот документ — единственный источник методики, результатов и обоснования
поисковых параметров проекта. Числа относятся к детерминированному профилю
`scale-1m`, а не к полному MIRACL и не к произвольному production-корпусу.

## Условия измерения

| Параметр | Значение |
|---|---|
| Корпус | 1 000 000 русских пассажей MIRACL |
| Запросы | все 1 252 MIRACL RU dev queries |
| Разметка | qrels для документов, попавших в профиль |
| Вектора | Castorini mDPR, 768 float32 |
| Функция близости | inner product |
| Глубина retrieval | top-30 |
| Глубина ranking-метрик | top-10 |

Профиль гарантированно содержит все размеченные документы и дополняется
детерминированным фоном из того же корпуса. Поэтому сравнение конфигураций
воспроизводимо, но значения нельзя объявлять официальным MIRACL benchmark.

Перед quality-прогоном workload останавливается, а зарезервированный DML-
диапазон очищается. Команда дополнительно проверяет, что в таблице ровно
исходный миллион строк: копии документов меняли бы и exact, и ANN top-k.

## Что и как считается

1. `exact` строит FAISS `IndexFlatIP` по всем миллиону document embeddings и
   сохраняет exact top-30 для каждого запроса. Это полный перебор, не ANN.
2. `evaluate` выполняет те же запросы в YDB через full-text, vector ANN и
   hybrid, сохраняя по 30 `docid`.
3. ANN recall@30 — средняя доля exact vector top-30, найденная YDB ANN top-30.
4. Для exact, full-text, vector и hybrid считаются метрики по MIRACL qrels.

Используемые qrel-метрики:

- **Recall@30 micro** — найденные релевантные документы, суммарно по запросам;
- **Recall@30 macro** — средний Recall отдельных запросов;
- **hit rate** — доля запросов хотя бы с одним qrel в top-30;
- **binary nDCG@10** — качество порядка первых десяти результатов;
- **MRR@10** — обратная позиция первого qrel в top-10.

ANN recall и qrel Recall отвечают на разные вопросы. Первый проверяет
приближённость YDB относительно exact поиска в том же векторном пространстве.
Второй проверяет соответствие выдачи экспертной разметке.

## Зафиксированный результат

Отчёт создан `2026-09-04T20:45:17Z` на текущей рабочей схеме.

| Метод | Recall@30 micro | Recall@30 macro | Hit rate | nDCG@10 | MRR@10 |
|---|---:|---:|---:|---:|---:|
| Exact vector | 0,935 | 0,940 | 0,978 | 0,718 | 0,761 |
| Full-text | 0,853 | 0,843 | 0,924 | 0,545 | 0,578 |
| YDB vector ANN | 0,827 | 0,828 | 0,911 | 0,662 | 0,721 |
| Hybrid | 0,894 | 0,895 | 0,950 | 0,668 | 0,725 |

Формальный **ANN recall@30 = 0,824760**.

Сохранены два основных артефакта:

- `artifacts/scale-1m-exact-top30.json.gz` — exact top-30, SHA-256
  `4fcac0b1d1c5082dcba54a97fe22a2b93de31ccc6cf297ea10934d179f3120b6`;
- `results/scale-1m-current.json.gz` — выдачи YDB и агрегаты, SHA-256
  `df051fa4a046bc4ecbd0fa9474e4de1f67d65cdf8a8034cc03a7dbe5547db030`.

`results/scale-1m-fulltext-ablation.json` содержит компактную
машиночитаемую сводку экспериментов, на которых выбрана полнотекстовая
конфигурация. Диагностический отчёт по текущему full-text запросу можно заново
получить штатной командой и поэтому он не считается источником итоговых метрик.

## Выбор полнотекстовой конфигурации

Измерения выполнялись на одних и тех же 1 252 запросах. В таблице показаны
кумулятивные изменения:

| Индекс и представление | Recall@30 | nDCG@10 |
|---|---:|---:|
| passage, standard tokenizer | 0,344 | 0,232 |
| + симметричная Unicode-нормализация | 0,362 | 0,229 |
| + русский Snowball | 0,578 | 0,333 |
| + `K1=1.0`, `B=0.25` | 0,669 | 0,414 |
| `title + passage`, те же настройки | 0,830 | 0,536 |
| + query-side `lexical_query` | **0,853** | **0,545** |

Выбор объясняется не одним «лучшим числом»:

- Snowball дал основной прирост за счёт русской морфологии.
- Симметричное удаление комбинируемого ударения U+0301 устраняет разные токены
  у визуально одинаковых слов; символ встречается в 289 запросах.
- Заголовок часто содержит ключевую сущность, поэтому индексируется единый
  `text = title + passage`, а не только passage.
- У корпуса сильно различается длина пассажей. Диапазон `B=0.2..0.3` оказался
  устойчивее стандартной сильной нормализации; выбран центр `B=0.25` и
  `K1=1.0`.
- `MinimumShouldMatch=25%` повысил Recall лишь до `0,852`, почти не изменил
  nDCG (`0,538`) и увеличил длительность последовательного прогона с 11,3 до
  220,6 с. При `75%` Recall упал до `0,567`. Для quality и hybrid оставлено
  `50%`.

`lexical_query` строится только из пользовательского вопроса: удаляет
частотный вопросительный каркас, но сохраняет числа, отрицание и имена. Он
повысил и качество, и селективность. На одинаковой топологии p95
последовательного full-text прогона снизился примерно с 352 до 172 мс, а p95
числа ранжируемых кандидатов — примерно с 80 до 51 тысячи.

Для отдельной performance-ветки используется более короткий
`fulltext_query` и `MinimumShouldMatch=100%`. Это модель keyword-поиска и
способ получить управляемую нагрузку; опубликованные quality-метрики она не
улучшает искусственно, потому что offline и hybrid продолжают использовать
`lexical_query` с 50%.

Остаточный разрыв full-text объясним семантикой qrels. У найденных в top-30
релевантных документов среднее буквальное покрытие термов запроса — около 51%,
у пропущенных даже в top-100 — около 26%. BM25 не обязан восстанавливать
название сущности из её описания, тогда как mDPR обучен на семантическую
близость.

## Выбор векторной конфигурации

Рабочий индекс:

```text
levels=2
clusters=128
overlap_clusters=3
KMeansTreeSearchTopSize=24
```

`levels/clusters/overlap_clusters` задают структуру дерева для миллиона
векторов. `SearchTopSize` задаёт ширину его обхода во время запроса и может
меняться без перестройки индекса.

Проверка `TopSize=32` дала ANN recall@30 около `0,854`, но vector и hybrid
раньше насыщали User и IC actor pools. `TopSize=24` сохранил ANN recall
`0,825`, vector qrel Recall `0,827` и позволил устойчиво выполнить смешанную
ступень `360/180/90` RPS на девяти узлах. Значения меньше 24 были дешевле, но
хуже по exact recall. Поэтому 24 — измеренный рабочий компромисс именно этого
стенда, а не общий default YDB.

Online vector возвращает top-10. Offline evaluation возвращает top-30, потому
что иначе формальный recall@30 посчитать невозможно.

## Выбор hybrid

Full-text и vector дополняют друг друга: в измеренной выдаче были запросы с
релевантным документом только в одной из двух веток. При этом vector сильнее
по первым позициям, поэтому равные веса и RRF переоценивали BM25.

После сетки по режиму fusion, весам и размеру пулов выбрана конфигурация:

```text
mode=linear
normalize=true
fulltext_weight=0.075
vector_weight=1.0
```

В offline-прогоне используются пулы `30/30` и итоговый top-30. Это дало qrel
Recall `0,894` против `0,827` у vector и nDCG `0,668` против `0,662`.
В online workload пулы `10/10` и итоговый top-10: это сохраняет смысл
демонстрации и не заставляет performance-профиль выполнять лишний result
lookup.

## Воспроизведение

Команды выполняются из корня проекта после `bootstrap` или активации
`scale-1m`. Основную нагрузку на время оценки остановить.

```bash
# Удалить только зарезервированные DML-строки, если workload уже запускался.
scripts/stand/run-workload-with-token.sh \
  -config config/workload.stand.json -dataset-profile scale-1m \
  -batch-size 1000 clean-dml

# Построить полный exact reference и выполнить три выдачи YDB.
bash scripts/quality.sh all scale-1m

# Напечатать пути, параметры и основные метрики сохранённого отчёта.
bash scripts/quality.sh status scale-1m
```

FAISS нужен только команде `exact` и устанавливается дополнительным Python-
extra:

```bash
.venv-data/bin/python -m pip install -e '.[model,quality]'
```

Если exact artifact уже построен и его SHA совпадает, можно повторить только
YDB-часть:

```bash
bash scripts/quality.sh evaluate scale-1m
```

Для диагностики стоимости каждого full-text запроса:

```bash
bash scripts/diagnose-fulltext.sh run scale-1m
bash scripts/diagnose-fulltext.sh status scale-1m
```

Она выполняет тот же production full-text запрос последовательно, со штатной
статистикой YDB. `scored_document_rows` — число строк внутренней таблицы
индекса, обработанных при ранжировании кандидатов; это не число результатов и
не обязательно чтения с диска. Диагностика нужна для анализа, но не заменяет
latency обычного workload.

## Как интерпретировать результат

- Параметры выбраны по качеству и стоимости вместе, а не по максимальному
  Recall любой ценой.
- Hybrid увеличил полноту, но не обязан побеждать vector на каждом запросе или
  каждой метрике.
- Числа фиксируют отсутствие явной деградации рабочего стенда. Для другого
  объёма, языка, encoder или формы запросов сетку нужно повторить.
- Observer может экспортировать сохранённые агрегаты в VictoriaMetrics, но
  основной demo-dashboard их не показывает: offline-метрики статичны и не
  должны отвлекать от эластичности и отказов.
