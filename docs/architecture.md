# Архитектура стенда

Этот документ описывает устройство решения и принятые инженерные решения.
Команды установки находятся в [deployment.md](deployment.md), а действия во
время показа — только в [demo.md](demo.md).

## Компоненты

```text
MIRACL RU corpus + qrels ─┐
Castorini document vectors ├─ data pipeline ─ runtime artifacts
public mDPR query encoder ─┘                         │
                                                    ▼
                                       Go workload ──► YDB
                                            │           │
                                     client metrics   YDB metrics
                                            └─────┬─────┘
                                                  ▼
                                     VictoriaMetrics + Grafana

chaos-md ── workload lifecycle / dynamic nodes / failures / annotations
```

Репозиторий отвечает за данные, схему, запросы, нагрузку и offline-оценку.
`chaos-md` отвечает за жизненный цикл процессов, изменение числа узлов,
хаос-воздействия и стек наблюдаемости. Кластер YDB уже должен существовать.

## Источники и воспроизводимость данных

Версии, контрольные суммы и URL зафиксированы в `config/sources.json`:

- MIRACL RU corpus: revision `d921ec7`, 9 543 918 пассажей;
- MIRACL RU dev topics и qrels: revision `5be20db`, 1 252 запроса;
- Castorini mDPR index: 9 543 918 векторов размерности 768, inner product;
- query encoder: `castorini/mdpr-tied-pft-msmarco-ft-miracl-ru`, revision
  `31e6284f3a77d1d61e16fd0f7f7d37b8c0346a81`;
- tokenizer: `bert-base-multilingual-cased`, зафиксированная revision,
  `max_length=32`, без L2-нормализации.

Document embeddings не пересчитываются: pipeline сопоставляет корпус и
готовый Castorini index по `docid`. Query embeddings вычисляются локально
соответствующим публичным checkpoint. Внешний inference API во время
подготовки или нагрузки не нужен.

Для каждого профиля сначала включаются все документы, отмеченные qrels. Фон до
нужного размера выбирается из того же корпуса seeded bottom-k hash с seed
`20260825`. Поэтому результат не зависит от порядка чтения файлов и повторяется
на другой машине. Профили `baseline-50k` и `scale-1m` самодостаточны и всегда
загружаются в чистое состояние одной таблицы.

Исходный архив Castorini имеет размер 27 177 739 148 байт и MD5
`b9460efd096292a1012ab1d27082498e`. Матрица отображается через memory map:
для её подготовки не требуется держать все вектора в RAM, но во время первой
распаковки нужно около 60 ГБ свободного диска.

## Runtime-артефакты

Профиль содержит промежуточные Parquet-файлы, manifest и два компактных файла,
которые читает Go-приложение:

```text
workload-documents.jsonl.gz  # документы и готовые embeddings
workload-queries.json.gz     # запросы, qrels и query embeddings
```

Сгенерированные данные находятся под `data/` и не входят в Git. SHA-256
записываются рядом с профилем. Активный профиль отмечается в gitignored-файле
`.runtime/active-dataset`; контроллер не позволяет незаметно смешать профиль
файлов и уже загруженную таблицу.

Для запроса сохраняются три представления:

- исходный естественный вопрос — вход публичного query encoder;
- `lexical_query` — нормализованный вопрос для BM25-ветки hybrid и оценки
  качества;
- `fulltext_query` — не более двух информативных термов для самостоятельного
  full-text потока нагрузки.

`lexical_query` удаляет вопросительный каркас и частотные служебные слова, но
сохраняет числа, отрицание и имена. `fulltext_query` моделирует прикладной
keyword-поиск по теме или сущности. Оба варианта строятся только из текста
запроса: qrels и содержимое релевантных документов не используются.

## Таблица и индексы YDB

Используется одна таблица, по умолчанию `deep_tech_search_documents`:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `Uint64` | первичный ключ |
| `docid` | `Utf8` | идентификатор MIRACL |
| `title` | `Utf8` | отображение результата |
| `text` | `Utf8` | нормализованный `title + "\n\n" + passage` |
| `embedding` | `String` | 768 float32 в бинарном представлении |

Пассаж не хранится второй раз в отдельной колонке. Полнотекстовый индекс
строится по `text`, векторный — по `embedding`; отдельного hybrid-индекса нет.

Рабочий полнотекстовый индекс:

```sql
GLOBAL USING fulltext_relevance
ON (text) COVER (title, docid)
WITH (
  tokenizer = standard,
  use_filter_lowercase = true,
  use_filter_snowball = true,
  language = "russian"
)
```

Рабочий векторный индекс:

```sql
GLOBAL SYNC USING vector_kmeans_tree
ON (embedding) COVER (title, docid)
WITH (
  similarity = "inner_product",
  vector_type = "float",
  vector_dimension = 768,
  levels = 2,
  clusters = 128,
  overlap_clusters = 3
)
```

`inner_product` соответствует исходному Castorini index. Менять функцию
близости без получения совместимых векторов нельзя.

## Запросы

Все runtime-запросы параметризованы. Текст и embedding не конкатенируются с
YQL. Файлы для YDB UI генерирует тот же Go builder; в них параметры только
заменены литералами, чтобы запрос можно было выполнить в браузере.

| Ветка | Конфигурация online workload |
|---|---|
| Full-text | `fulltext_query`, `Or`, `MinimumShouldMatch=100%`, `K1=1.0`, `B=0.25`, top-10 |
| Vector | inner product, `KMeansTreeSearchTopSize=24`, top-10 |
| Hybrid | `lexical_query` + тот же query embedding, linear fusion, normalize, веса `0.075/1.0`, пулы `10/10`, top-10 |

Offline-оценка использует более глубокий top-30. Для полнотекста и hybrid там
применяется `lexical_query` с `MinimumShouldMatch=50%`; у hybrid пулы `30/30`.
Разница преднамеренная: performance workload не должен выполнять лишние
result lookup, а оценке нужна достаточная глубина.

Почему выбраны именно эти значения и какие альтернативы были измерены,
зафиксировано в [quality/README.md](../quality/README.md).

## Загрузка и DML

Первичная загрузка выполняется `BulkUpsert` до создания индексов. После
создания синхронного векторного индекса изменения выполняются обычным DML.

Стендовый профиль включает 7 проверяемых DML-операций в секунду. При запуске
из runtime-файла берётся пул из 50 000 полных документов вместе с их
embeddings. Каждая операция записывает документ в зарезервированный диапазон
ключей и проверяет видимость маркера через полнотекстовый индекс. Это один
логический сценарий `DML + проверка`; отдельным видом пользовательского поиска
он не считается.

Пул не создаёт синтетических embeddings и впервые повторяет ключ примерно
через 119 минут. Повтор означает `UPSERT` существующего ключа, а не рост
таблицы без границ. `clean-dml` удаляет только зарезервированный диапазон.

## Эластичность и управление состоянием

Основная таблица создаётся с load- и size-based auto partitioning и пределом
64 партиции. Для короткой демонстрации уже полученная топология заранее
прогревается на девяти dynamic-узлах. Минимумы `base=64`, `fulltext=16` и
`vector=9` — защитные нижние границы данного стенда: они не создают партиции,
а не позволяют прогретой ёмкости склеиться обратно.

Первый кадр демонстрации намеренно отличается только для полнотекста:
`ft_idx` пересоздаётся с одной фиксированной рабочей партицией. Затем нагрузка
показывает потолок этой таблетки, команда `fulltext-split` включает auto split,
и индекс делится. Основная таблица и векторный индекс сохраняют прогретую
топологию, чтобы не добавлять случайные split/merge в тот же момент.

На следующем этапе профиль нагрузки меняется с `120/60/30` на `288/144/72`
RPS (full-text/vector/hybrid), а число dynamic-узлов — с 3 до 9. В workload
нет очереди просроченных заданий: если open-loop генератор не может вовремя
начать запрос, счётчик показывает пропуск, но старый трафик не обрушивается на
YDB после восстановления.

Единственная штатная точка управления демонстрацией — `scripts/demo.sh`.
Низкоуровневые команды сохраняются для диагностики, но в операторском
сценарии не требуются.

## Наблюдаемость и хаос

Go workload экспортирует фактический RPS, target, p95, ошибки, ретраи, DML и
пропуски генератора. Observer независимо читает системную статистику YDB и
экспортирует загрузку таблеток, партиции и последний offline-отчёт качества.
Node exporter даёт загрузку actor pools по узлам.

VictoriaMetrics собирает эти три источника. Grafana показывает два ряда
динамических графиков; статические сведения о размере корпуса и offline-
качестве намеренно не вынесены на основной demo-dashboard. `chaos-md` создаёт
подписанные region-аннотации начала и конца изменяющих состояние этапов.
Read-only проверки аннотаций не создают.

## Границы применимости

- Это инженерный стенд и детерминированный 1M-subset, а не официальный
  MIRACL benchmark и не продуктовый SLA.
- Числа качества и производительности относятся к зафиксированным данным,
  параметрам и проверенной сборке YDB; для другой версии capability probes,
  `preflight` и калибровку нагрузки нужно повторить.
- Offline quality требует ровно исходный миллион строк. После DML сначала
  выполняется `clean-dml`.
- Prefix filtering поддерживается проверенной сборкой, но не входит в основной
  сценарий и не влияет на опубликованные результаты.
- Масштабирование демонстрирует распределение конкретной смешанной нагрузки;
  оно не заявляется как универсально линейное для любых запросов и схем.
- Исходные тексты и вектора не перепубликуются из-за условий исходных наборов;
  pipeline загружает их у издателей.
